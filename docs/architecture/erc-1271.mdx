description: "How Arca validates off-chain signatures generated by smart contract wallets."

Standard EVM cryptography assumes that every account is an **Externally Owned Account (EOA)**, meaning it is controlled by a private key. In an EOA architecture, validating a signature is simple: the smart contract calls the EVM opcode `ecrecover(hash, v, r, s)`, which recovers the public key that signed the data, and checks if it matches the user's address.

However, **Smart Contract Accounts (Modular Wallets)** do not have private keys. They are smart contracts, and standard `ecrecover` will recover an arbitrary address, causing signature verification to fail.

To resolve this and support modular wallets, Arca implements **ERC-1271 (Standard Signature Validation Method for Contracts)**.

---

## 1. What is ERC-1271?

**ERC-1271** is an Ethereum Improvement Proposal that defines a standard interface for smart contracts to validate signatures. 

When a user's wallet is a smart contract, the billing contract cannot verify the signature internally. Instead, the billing contract must *delegate* signature validation by making a static call to the subscriber's wallet contract, passing the message hash and the signature, and asking: *"Is this signature valid for your account?"*

```
   EOA Signature Verification (Metamask)
   ┌──────────────────┐
   │ subscribeWithSig │ ──> [ ecrecover(hash, sig) ] ──> Matches Subscriber Address?
   └──────────────────┘

   Smart Account Signature Verification (Arca / ERC-1271)
   ┌──────────────────┐
   │ subscribeWithSig │ ──> Staticcall to Subscriber Wallet ──> [ isValidSignature(hash, sig) ]
   └──────────────────┘                                                  │
                                                                         ▼
                                                          Returns Magic Selector 0x1626ba7e?
```

---

## 2. The Cryptographic Interface & Magic Values

The ERC-1271 standard defines a single interface that every compliant modular smart account must implement:

```solidity
interface IERC1271 {
    /**
     * @dev Should return whether the signature provided is valid for the provided data
     * @param _hash      Hash of the data to be signed
     * @param _signature Signature byte array associated with _hash
     *
     * MUST return the bytes4 magic value 0x1626ba7e if the signature is valid.
     */
    function isValidSignature(bytes32 _hash, bytes calldata _signature) external view returns (bytes4 magicValue);
}
```

The success return value is a specific **Magic Selector**:
* **`0x1626ba7e`**: The bytes4 representation of `bytes4(keccak256("isValidSignature(bytes32,bytes)"))`. This indicates the signature is **valid**.
* **Any other value** (e.g. `0xffffffff`): Indicates the signature is **invalid**.

## 3. Implementation in `SubscriptionGateway.sol`

When the Autopay Relayer calls the `subscribeWithSignature` function, the gateway contract constructs the EIP-712 message hash and validates the ERC-1271 signature directly against the subscriber's contract address:

```solidity
function subscribeWithSignature(
    address subscriber,
    address sessionPublicKey,
    bytes32 planId,
    uint256 tierId,
    uint256 maxCycles,
    uint256 deadline,
    bytes calldata signature,
    string calldata buyerData
) external {
    // ... validation steps ...

    // Construct EIP-712 message hash
    bytes32 messageHash = keccak256(
        abi.encodePacked(
            "\x19\x01",
            DOMAIN_SEPARATOR,
            keccak256(
                abi.encode(
                    AUTHORIZE_SESSION_KEY_TYPEHASH,
                    subscriber,
                    sessionPublicKey,
                    planId,
                    tierId,
                    maxCycles,
                    deadline
                )
            )
        )
    );

    // Verify signature directly on the subscriber contract wallet via ERC-1271 staticcall
    require(
        IERC1271(subscriber).isValidSignature(messageHash, signature) == 0x1626ba7e,
        "Invalid signature"
    );

    // ... process payment and update state ...
}
```

## 4. Key Advantages of ERC-1271 in Arca

By delegating signature validation to the smart wallet contract itself, Arca gains massive security advantages required for institutional billing:

### Support for Any Wallet Logic
The smart wallet contract can verify signatures using any arbitrary security configuration. It can use standard ECDSA, multi-signature logic (e.g. 3 of 5 keys must sign), secure enclave keys (passkeys), or quantum-resistant signatures. The gateway contract remains fully chain-agnostic to the wallet's internal security logic.

### Social Recovery & Key Rotation
If a user rotates their keys (for instance, if they lose their device and execute a social recovery contract to bind their wallet to a new key), old signatures are automatically invalidated. The ERC-1271 call will recover the new key, ensuring that compromised keys cannot trigger billing.

### Fine-Grained Permissions
Smart accounts can deploy modular permission plugins. A user can configure a plugin that specifically allows only certain relayers or limits the maximum gas fees they are willing to refund. ERC-1271 verifies that the signature satisfies these granular, contract-enforced constraints.
